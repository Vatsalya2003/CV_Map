# LLM Usage Log

Plain-language log of what was asked of the LLM (Claude) at each step, for the report's acknowledgement section.

- 2026-08-11: Asked Claude to draft the overall implementation plan for the project (repo structure, phased build order, detection class subset options) before writing any code. Chose the "broad" COCO class subset (person, chair, couch, dining table, potted plant, backpack, bench, refrigerator, oven, sink, tv, bed) to approximate indoor obstacles since COCO has no "door" class.
- 2026-08-11: Reviewed the implementation plan a second time with Claude and had it flag/fix gaps: unused "near" bucket, missing FPS/performance handling, single global confidence threshold, missing two-pass labeling for detection vs. decision metrics, IEEE report page/reference requirements, and an ambiguous "center-straddling" zone rule. Resolved center-straddle by defining a 10%-of-frame-width margin around the midline where boxes count toward both zones.
- 2026-08-11 (Phase 0): Had Claude set up the Python 3.12 venv, install ultralytics/pyttsx3/opencv-python, verify MPS acceleration works (confirmed available/built), confirm YOLOv8n loads with all 80 COCO classes, freeze requirements.txt, and add a .gitignore (venv/, weights, caches).
- 2026-08-11 (Phase 1): Had Claude write detector.py (YOLOv8n wrapper filtered to our 12-class subset, per-class confidence thresholds) and utils.py (debug box/FPS drawing), following the required file structure convention (header, main(argv), guard). Sanity-tested on a real webcam frame: correctly detected a person with a real bounding box, measured ~10.9 FPS on MPS.
- 2026-08-11 (Phase 2): Had Claude write distance.py (box height + vertical position -> far/near/very_near closeness bucket), zones.py (left/right split with a 10%-of-frame-width center margin so midline obstacles count toward both zones, worst-case bucket per zone, decision table -> "path clear"/"obstacle left"/"obstacle right"/"stop"), and guidance.py (pyttsx3 TTS that only speaks when the decision changes or a 1.5s cooldown passes, run on a background thread so it doesn't block the frame loop). Verified each file's built-in sanity test independently: distance.py correctly buckets three example boxes into far/near/very_near, zones.py correctly returns clear/move-right/stop for three example scenes, and guidance.py's debounce correctly skips a repeated identical decision inside the cooldown window. Confirmed pyttsx3 has 184 real system voices available on this Mac, not silently failing.
- 2026-08-11 (wiring): Had Claude write main.py, wiring detector -> distance/zones -> guidance -> debug overlay into one capture loop. It supports either the live webcam or a recorded video file, an optional PROCESS_EVERY_N frame-skip (currently 1, i.e. every frame, since FPS is fine), and --save/--no-window flags for headless test runs. Verified end-to-end on a short recorded test clip: pipeline ran at ~18.75 FPS, and a saved frame correctly showed a person's box straddling the left/right midline triggering "decision: stop" with both zones reporting very_near.
- 2026-08-11 (Phase 3 tooling): Had Claude add a --log flag to main.py that writes a per-frame CSV (results/log_<clip>.csv: frame, decision, left_status, right_status, detections) for the two Phase 3 labeling passes. While testing this, found and fixed a real bug in guidance.py: pyttsx3's engine.runAndWait() is not safe to call from multiple threads at once, and spawning a new thread per spoken sentence caused "run loop already started" crashes when the decision changed quickly. Fixed by switching to one persistent background worker thread pulling from a queue.Queue, so sentences are spoken one at a time in order instead of racing.
- 2026-08-11 (Phase 3 first real footage): Vatsalya recorded 3 real iPhone clips of the apartment (open floor test, chairs-on-one-side test, table-blocking-path test) and added them to test_footage/. Had Claude check orientation (iPhone videos read correctly as portrait by OpenCV on macOS, no rotation fix needed), run the full pipeline with --log and --save on all three, and spot-check sample frames. Results looked correct: chairs on one side stayed "path clear" until close enough, a table+chair blocking the hallway correctly triggered "stop" with the table box spanning the midline. Also found a real false negative: a chair cropped at the top frame edge in IMG_5078 was completely missed by YOLO, so the decision said "right: clear" when a large near obstacle was actually there - worth noting in the report's limitations/failure cases section.
- 2026-08-11 (Phase 3 evaluation - full loop): Given the deadline, had Claude do the ground-truth labeling itself (viewing sampled frames and contact sheets) instead of asking Vatsalya to hand-label ~157 frames. Built extract_labeling_samples.py (samples every 15th logged frame, saves the image, builds a labeling_template_<clip>.csv with the pipeline's own prediction next to blank ground-truth columns), build_contact_sheets.py (arranges sampled frames into labeled grids so many can be reviewed at once), label_ground_truth.py (records the manual judgments for a representative ~10-frame-per-clip subset, 26 total), and evaluate.py (computes detection precision/recall and decision accuracy from the labeled rows only).
  First labeling pass (done from resized contact-sheet thumbnails) had real left/right errors - e.g. an oven that is objectively right-of-center by its bounding box got called "obstacle left". Caught this by cross-checking bbox center-x against the frame midline for every labeled row and re-viewing full-resolution frames for anything that disagreed, then relabeled. This matters for the report: it's an example of a labeling-quality check, not just a pipeline check.
  After relabeling, decision accuracy was low on IMG_5078 (0.40) specifically because the algorithm was calling "path clear" when a human would already flag an obstacle - the very_near-only decision rule (near is informational only) was too conservative for real hallway footage. Tried promoting "near" to also block a zone in zones.py. This fixed the IMG_5078 hallway-chair cases but broke IMG_5077's kitchen-appliance cases: box-height-ratio is a poor distance proxy for objects that are just physically large (an oven looks "near" from its height alone even from across the room, since real ovens are tall), so kitchen counters started false-triggering "obstacle"/"stop". Measured net accuracy across all 26 labeled frames both ways: near-blocks-too scored 13/26 (50%), very_near-only scored 15/26 (58%). Reverted to very_near-only since it was actually better in aggregate, and documented the comparison directly in zones.py's decide() so the reasoning is visible in the code, not just here.
  Final numbers used for the report: detection precision 0.82, recall 0.89, decision accuracy 0.58 (26 hand-labeled frames across 3 clips). Per-clip decision accuracy is uneven (IMG_5077 0.88, IMG_5078 0.40, IMG_5079 0.50) - IMG_5078 pulls the average down mainly because of the missed-detection case and the appliance/near-threshold tradeoff above, both genuine, explainable failure modes worth discussing in the report rather than hiding.
- 2026-08-11 (phone app, web version): Vatsalya asked for a phone app to run the demo with audio on the phone. Given ~2 days to the deadline, discussed the tradeoff between a real native iOS app (Swift + CoreML conversion + Xcode, realistically 1-2+ days) versus a small local web app (Flask server on the Mac + a page the phone opens in Safari), and chose the web app for speed and lower risk to the report/video deliverables. Had Claude build web_app.py (Flask server reusing detector.py/zones.py exactly as-is, one /process endpoint that takes a JPEG frame and returns the decision + boxes as JSON) and templates/index.html (opens the phone's rear camera via getUserMedia, sends a frame every ~600ms, draws returned boxes on a canvas overlay, and speaks the decision using the browser's built-in SpeechSynthesis API with the same change-or-cooldown debounce logic as guidance.py, just reimplemented in JavaScript).
  Debugging the phone connection took several real steps: (1) Flask's ssl_context="adhoc" self-signed cert has no Subject Alternative Name field, which modern iOS Safari silently rejects (loads about:blank, no warning at all) even though desktop Safari accepts it - confirmed by generating a proper openssl cert with a SAN for the LAN IP, which still didn't fully resolve it on iOS; (2) switched to running Flask as plain HTTP locally and fronting it with an ngrok tunnel instead, which terminates HTTPS with a real publicly-trusted certificate - this worked immediately and also removed the "must be on the same WiFi" requirement; (3) even after the page loaded, there was no audio - iOS Safari requires speechSynthesis.speak() to be called synchronously inside a genuine user-gesture handler (like the Start button's click) at least once before it will allow any later speak() calls (like the ones triggered from async fetch responses) to actually produce sound. Fixed by speaking one empty utterance directly inside the click handler to "unlock" audio for the rest of the page's lifetime. Also added a visible on-screen "speaking: ..." indicator to make future audio debugging easier (distinguishes "code never called speak()" from "device is muted").
- 2026-08-11 (expand detector classes): After trying the phone demo, Vatsalya asked for two things: more accurate "path clear" calls, and more object classes recognized. Clarified that a plain featureless wall genuinely cannot be detected by an object detector (YOLO finds specific classes like "chair", not generic architecture) - this is an intentional scope limitation (no depth estimation/SLAM per the project plan), not a bug, and got documented as a known limitation for the report rather than "fixed". For the class list, added toilet, microwave, laptop, vase, suitcase, and book to detector.py's OBSTACLE_CLASSES (was: person, chair, couch, dining table, potted plant, backpack, bench, refrigerator, oven, sink, tv, bed), chosen deliberately with Vatsalya rather than picked silently, per the project's own rule about not expanding classes without checking in.
